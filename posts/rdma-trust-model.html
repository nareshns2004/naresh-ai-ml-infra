The kernel can’t see your tensors: RDMA’s trust model

RDMA is fast because it takes the remote CPU and kernel out of the data path. That is also why every host-based security control you own goes blind the moment the gradients start moving.

Naresh Kumar · Nov 2026 · 8 min read

TL;DR
  • With one-sided RDMA WRITE (and GPUDirect RDMA), the NIC places data straight into registered, often GPU, memory. The receiving host’s network stack, netfilter and eBPF hooks never see the payload.
  • Authorisation is a capability: a 32-bit rkey plus an address, carried in the clear in every WRITE’s header. Research has shown key generation and other protections to be weaker than assumed (ReDMArk).
  • So the controls belong where the data path is: in the NIC and the fabric. That means per-tenant protection domains and partitions, short-lived memory windows instead of long-lived keys, inline encryption, and telemetry at the NIC or DPU.

What actually authorises a remote write

The receiver registers a memory region (for GPUDirect, a slice of GPU memory) under a protection domain, and gets back an rkey. It hands the peer an (address, rkey) pair. From then on, any RDMA WRITE that arrives on a queue pair in that protection domain, with a matching rkey and an address inside the region, is placed into memory by the NIC. No interrupt, no syscall, no policy check in software.

Three things follow. The rkey is a bearer capability: whoever holds it can write. It travels in plaintext in each WRITE packet’s RDMA extended transport header, so anyone who can observe the fabric learns it. And it is 32 bits, long-lived for as long as the region stays registered. For a KV-cache pool registered once at startup, as most disaggregated-inference transports do for speed, that is the life of the server.

Reading the calculator

At full 32-bit entropy, a modest guess rate and a handful of long-lived regions, an off-path attacker gets there in days, and “registered at startup” means the key lives longer than that. Drop the effective entropy (key generation that is less random than it looks was one of ReDMArk’s findings) and it’s minutes. The lever that changes the shape of the curve is lifetime. A type-2 memory window, bound per transfer and invalidated when the transfer ends, turns a server-lifetime capability into a milliseconds-lifetime one.

That isn’t only a security property. It is the same mechanism that stops a delayed write from a timed-out transfer from landing in a KV block that has since been reused: the NIC rejects it with a remote access error. In kvwire this is ADR-0005: per-transfer memory windows are the first option for stale-write fencing, to be decided on measured bind cost. Correctness and security want the same thing here, which is the best kind of security control: it pays for itself.

Notice the last column. None of these controls sits in software on the per-message path, which is what makes them deployable on a fabric whose whole reason to exist is microseconds.

Model & assumptions

  • Guessing model: keys uniformly random over 2b values, k valid keys exposed, independent guesses at rate g. Expected time to first hit ≈ 2b / (g·k); probability of a hit within lifetime T = 1 − (1 − k/2b)g·T.
  • On a reliable-connected QP, a wrong rkey typically produces a remote access error that moves the QP to the error state, so each guess costs a reconnect. Use the guess-rate slider to model that; the rate is the attacker’s, not a NIC spec.
  • An on-path attacker (mirror port, compromised switch, shared segment) needs no guesses: the rkey and remote address are carried unencrypted in each WRITE request. This is the strongest argument for inline encryption and partitioning.
  • “Not on the data path” refers to one-sided operations offloaded to NIC hardware. Connection setup, and software RDMA implementations such as rxe, do traverse the kernel.
