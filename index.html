Work

Three problems I work on

AI lab infrastructure splits along three lines: keep the job running, make each GPU-hour count, and make sure nobody else gets to use either. Kernel and fabric depth is the foundation for all three.

Reliability at scale

goodput fault-tolerant training orchestrator

Problem
One bad GPU, NIC, cable or switch port stalls a collective, and every rank times out the same way.
Why it’s hard
Symptoms are global and causes are local. Stock tooling detects in minutes, attributes nothing, and restarts the whole job, sometimes onto the same broken hardware.
Approach
Inject faults with a ground-truth ledger, capture NCCL flight-recorder signatures, and correlate them with DCGM and NIC telemetry to name the culprit rank and component. Correct attribution makes small recoveries safe: re-init communicators in-process, replace one node, or restore from a peer’s in-memory checkpoint.
Status
M1 of 6 · in progress  No results measured yet; every future number will link to a run.
Hugging Face
The injector’s ledger labels every incident by construction. That data trains one model, a grounded root-cause tier (Qwen3 + LoRA) whose verdicts cite evidence ids, so a script scores every answer against the ledger. A Space adds a signature-matching fast tier. To take goodput’s classifier slot, the model must beat goodput’s own rules, the zero-shot base model and a majority baseline. design

Efficiency at scale

kvwire disaggregated inference engine

Problem
Prefill is compute-bound, decode is memory-bandwidth-bound. Colocated, they interfere: prefills spike TPOT, decodes spike TTFT.
Why it’s hard
Disaggregation trades interference for data movement. The KV cache has to cross the network before decode can start, and has to stay correct when the network fails mid-transfer.
Approach
A GPUDirect RDMA transport, a Triton KV re-layout kernel (kept only if the data justifies it), and a failure-aware coordinator. It plugs into vLLM through the KV connector interface and replaces the parts that move bytes and decide what to do when moving bytes goes wrong.
Status
M1 · in progress  Baselines and hardware ceilings first; results cells stay “—” until measured.
Hugging Face
Every measured transfer becomes a row in a public dataset, next to its perftest ceiling and the prefill time it would take to recompute instead. A Space answers “move the KV cache or recompute it?” from measured rows only: no simulation, no extrapolation. planned

Trust at scale

Secure by construction zero trust for GPU fabrics, model artifacts and AI agents

“Assume the model will be fooled. Design so that being fooled is cheap.”

Problem
The fastest paths in an AI cluster are the least watched. RDMA bypasses the host kernel, so firewalls and eBPF never see it. Checkpoints are programs: pickle runs code on load. And AI agents now hold the credentials, taking instructions from whatever they read.
Why it’s hard
Every control costs latency or bandwidth on hardware that is billed by the second, so security that slows the step gets turned off. The work is finding the controls that sit off the hot path: at the NIC, in the artifact format, at the tool boundary.
Approach
Threat-model each layer against real incidents, then build the control into the system rather than bolting it on. Already in my repos: goodput’s fault injector is default-deny. It acts only on allowlisted hosts, every fault carries an auto-revert watchdog, destructive mechanisms need an explicit opt-in, and GPU resets, firmware and switch changes are never automated (SECURITY.md). kvwire’s ADR-0005 evaluates per-transfer memory windows, invalidated before a KV block is reused, so the NIC itself rejects a late or stray write.
Status
safety invariants in code fencing ADR proposed goodput RCA tier: recommends, never acts · planned  Plus five interactive security posts below.

NIC counter → step-time attribution nicprof

The gap: a 512-GPU job slows down; the network team has millions of counter series, the ML team has a step-time graph, and nobody can say which counter explains which millisecond.

What it does: aligns RDMA/ethtool/SR-IOV counters to each rank’s step windows, fits a non-negative model of excess step time, and traces PFC pause back to its origin so a victim port isn’t blamed as the cause. NIC-side telemetry is also where kernel-bypass traffic becomes visible at all.

Runnable demoSource ↗

Kernel performance toolkit kptk

The gap: “CPU 80%” and “THP on” don’t explain why a workload is slow.

What it does: explains slowness from kernel evidence (run-queue delay, allocation vs access NUMA locality, THP fallback and compaction stalls) and calls perf_event_open(2) directly with multiplexing correction. Standard library only, 43 tests.

Runnable demoSource ↗

Pickle opcode disassembler & scanner in-browser

The gap: “don’t load untrusted checkpoints” is advice; seeing GLOBAL os system sitting inside a model file is understanding.

What it does: a dependency-free pickle-protocol disassembler that steps through a checkpoint’s opcodes on a stack machine and flags every import outside a weights-only allowlist, next to a safetensors header parser for contrast.
